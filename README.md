# GuildOfComfort

Приложение для учёта монтажных работ (автоматика, вентиляция, электрика,
кондиционирование): объекты → подпроекты → задачи на основе справочника
операций с технологическими картами, складской учёт материалов по объектам,
табель монтажников и приватные финансовые расчёты.

Три роли: **администратор**, **монтажник**, **заказчик** (монтажники и
заказчики регистрируются сами на `/register`, администратор создаётся через
seed-скрипт).

## Стек

- Next.js 16 (App Router, TypeScript), Server Actions
- PostgreSQL + Prisma 7 (`@prisma/adapter-pg`)
- Своя аутентификация: пароли — bcrypt, сессия — JWT в httpOnly-cookie (jose)

## Запуск в разработке

1. Поднимите PostgreSQL. Вариант с Docker (`docker-compose.yml` в корне):

   ```bash
   docker compose up -d
   ```

   Либо используйте локально установленный PostgreSQL — создайте базу и
   пользователя, соответствующие `DATABASE_URL` в `.env`.

2. Скопируйте `.env.example` в `.env` и при необходимости поправьте значения:

   ```bash
   cp .env.example .env
   ```

3. Установите зависимости, накатите миграции и сид (создаёт администратора
   и базовый справочник материалов):

   ```bash
   npm install
   npx prisma migrate dev
   npx prisma db seed
   ```

   Данные администратора по умолчанию: `admin@guildofcomfort.local` /
   `ChangeMe123!` (переопределяются переменными окружения `ADMIN_EMAIL` /
   `ADMIN_PASSWORD` перед запуском сида). **Смените пароль после первого
   входа** — отдельного экрана смены пароля пока нет, обновите
   `passwordHash` пользователя напрямую или создайте нового администратора
   через сид с новыми переменными окружения.

4. Запустите dev-сервер:

   ```bash
   npm run dev
   ```

   Приложение доступно на http://localhost:3000.

## Модель работы

- Администратор создаёт **объект**, на объекте — **подпроекты**, в
  подпроектах — **задачи**. Каждая задача основана на **операции** из
  справочника; у операции есть технологическая карта (инструменты и
  материалы).
- У каждого объекта — свой **склад**. При завершении задачи монтажник
  списывает материалы (по умолчанию — по норме из техкарты, значение можно
  скорректировать по факту). Списание блокируется, если материала не
  хватает на складе.
- Жизненный цикл задачи: Свободна → Назначена → В работе → (Пауза /
  Блокировка, с обязательной причиной) → В работе → На проверке →
  Выполнена. Проверяет и принимает задачи администратор.
- Табель и финансовые записи — приватный раздел: монтажник видит только
  свои записи, заказчик их не видит вовсе.

## Авторизация и разграничение доступа

Каждый серверный компонент и каждое server action самостоятельно проверяет
сессию и роль (`src/lib/session.ts`), а данные всегда выбираются с
фильтром по владению (объект/задача/участник). `src/proxy.ts` (аналог
middleware в Next.js 16) выполняет только оптимистичный редирект по роли на
основе cookie — не является источником истины по авторизации.

Изначально в плане предполагалась защита на уровне PostgreSQL (Row Level
Security). От неё в MVP отказались: приложение работает через один пул
соединений с Prisma, и корректная RLS потребовала бы прокидывать
`SET app.user_id/app.role` в каждую транзакцию по всему кодовому пути —
это отдельная по объёму задача с реальным риском регрессий. Вместо этого
авторизация полностью реализована и проверена на уровне приложения
(см. `.scratch`-сценарии, использованные при разработке). Добавление RLS
как дополнительного рубежа защиты — хороший кандидат на следующую
итерацию, когда основной функционал обкатается в реальном использовании.

## Структура

```
prisma/schema.prisma        — модель данных
src/app/actions/            — server actions (мутации)
src/app/admin/               — кабинет администратора
src/app/installer/           — кабинет монтажника
src/app/customer/            — кабинет заказчика
src/lib/                     — auth, session, prisma client, лейблы статусов
src/proxy.ts                 — редиректы по ролям (бывший middleware)
```
